# 기능 목록 및 고도화 포인트

## 문서 목적

이 문서는 보건소 스마트 예약·대기 및 혼잡도 분석 시스템에서 앞으로 만들어야 할 기능을 전체적으로 정리하고, 각 기능에서 놓치기 쉬운 고도화 포인트를 현재 프로젝트에 맞춰 정리한다.

나중에 포트폴리오를 작성할 때 단순 CRUD 구현이 아니라, 사용자 경험, 도메인 정책, 동시성, 권한, 통계, 운영 관점까지 고려했다는 점을 설명할 수 있도록 기능별 어필 포인트도 함께 기록한다.

## 개발 접근 방향

이 프로젝트는 백엔드만 먼저 완성하거나 프론트엔드만 먼저 완성하는 방식보다, 아래 순서로 진행하는 것이 적합하다.

```text
사용자 흐름 정의
→ 화면 단위 UX 초안 작성
→ API 계약 정의
→ Mock API 또는 mock data로 프론트 흐름 검증
→ 백엔드 구현
→ 프론트 실제 API 연동
→ 예외, 권한, 상태 전이, 통계 검증
```

이유:

- 예약·대기 시스템은 사용자의 화면 흐름과 현장 직원의 업무 흐름이 중요하다.
- 화면에서 필요한 데이터 모양을 먼저 이해해야 API 응답이 과하거나 부족하지 않다.
- 백엔드 도메인 정책은 반드시 지켜야 하므로, UX에 맞추되 핵심 규칙은 서버에서 검증해야 한다.
- 프론트와 백엔드가 API 계약을 기준으로 병렬 작업할 수 있다.

결론:

- 프론트를 완전히 먼저 만들기보다는, 화면 흐름과 API 계약을 먼저 잡는다.
- 그 다음 프론트는 mock data로 흐름을 확인하고, 백엔드는 계약에 맞춰 구현한다.
- 이 프로젝트에서는 `UX-first + API-first + backend domain validation` 방식이 가장 적합하다.

## 1. Common Context

### 만들어야 할 기능

- 공통 응답 형식
- 공통 오류 응답 형식
- ErrorCode
- CustomException
- GlobalExceptionHandler
- 공통코드 조회 API
- 공통코드 seed 데이터

### 고도화 포인트

| 항목 | 내용 |
|---|---|
| 오류 코드 표준화 | 프론트에서 오류별 안내 문구를 쉽게 처리할 수 있도록 코드값을 고정한다. |
| 한글 메시지 | 공공서비스 성격에 맞게 사용자에게 보이는 메시지는 한글로 명확히 작성한다. |
| 공통코드 캐시 | 공통코드는 자주 조회되므로 groupCode 기준 메모리 캐시를 고려한다. |
| Enum 연계 | 상태 전이는 Java Enum, 화면 표시명은 DB 공통코드로 분리한다. |
| Swagger 문서화 | 공통 응답과 오류 응답 예시를 Swagger에서 확인 가능하게 한다. |

### 포트폴리오 어필 포인트

- API 응답을 프로젝트 전반에서 일관되게 설계했다.
- DB 공통코드와 Java Enum의 역할을 분리해 운영 유연성과 도메인 안정성을 함께 고려했다.

## 2. Office Context

### 만들어야 할 기능

- 보건소 기본 정보 조회
- 업무 유형 조회
- 업무 유형 관리자 등록/수정
- 창구 조회 및 관리
- 직원 담당 업무 배정

우선 API:

```text
GET /api/service-types
```

### 고도화 포인트

| 항목 | 내용 |
|---|---|
| 업무 유형 기준정보화 | 예방접종, 건강검진/검사, 건강상담은 공통코드가 아니라 `service_types`로 관리한다. |
| 다중 보건소 확장 | MVP는 단일 보건소지만 `health_center_id`를 포함해 확장 가능하게 둔다. |
| 활성 여부 | 업무 유형과 창구는 삭제보다 비활성화 중심으로 관리한다. |
| 기본 정원 | 업무 유형별 기본 예약 가능 인원을 관리한다. |
| 화면 최적화 응답 | 프론트 업무 선택 화면에 필요한 `id`, `code`, `name`, `description` 중심으로 응답한다. |

### 포트폴리오 어필 포인트

- 공통코드와 기준정보의 차이를 구분했다.
- 예약 도메인의 선행 기준정보를 별도 Context로 분리해 확장성을 고려했다.

## 3. Auth/Member Context

### 만들어야 할 기능

- 로그인
- Access Token 발급
- Refresh Token 발급 및 재발급
- 로그아웃
- Role 기반 권한 검증
- 회원, 직원, 관리자 seed 계정

### 고도화 포인트

| 항목 | 내용 |
|---|---|
| Bearer 통일 | Swagger와 실제 필터 모두 `Authorization: Bearer {token}` 형식으로 통일한다. |
| Refresh Token 저장 | 재발급과 로그아웃 처리를 위해 DB 저장 방식을 고려한다. |
| 권한 분리 | CITIZEN, GUARDIAN, STAFF, ADMIN 권한을 API별로 명확히 제한한다. |
| 비밀번호 보안 | seed 계정도 실제와 같은 password encoder를 사용한다. |
| 민감값 분리 | JWT secret, DB password는 운영 전 환경변수로 분리한다. |

### 포트폴리오 어필 포인트

- 단순 로그인 구현이 아니라 Access/Refresh Token과 권한 기반 API 보호를 설계했다.
- 공공서비스에서 필요한 역할 분리를 도메인 요구사항과 연결했다.

## 4. Reservation Context

### 만들어야 할 기능

- 예약 가능 슬롯 조회
- 예약 신청
- 내 예약 목록 조회
- 예약 상세 조회
- 예약 취소
- 관리자 예약 슬롯 생성
- 관리자 슬롯 정원 조정

### 핵심 정책

| 정책 | 내용 |
|---|---|
| 예약 단위 | 30분 |
| 예약 가능 기간 | 오늘부터 14일 |
| 당일 예약 | 허용 |
| 기본 정원 | 업무별 5명 |
| 예약 취소 | 방문 1시간 전까지 가능 |
| 중복 방지 | 동일 사용자 동일 시간대 중복 예약 제한 |
| 정원 초과 방지 | 슬롯 capacity 초과 예약 불가 |

### 고도화 포인트

| 항목 | 내용 |
|---|---|
| 동시성 제어 | 마지막 남은 슬롯에 여러 사용자가 동시에 예약할 때 정원 초과가 발생하지 않게 한다. |
| 조건부 update | `reserved_count < capacity` 조건으로 증가 처리하는 방식을 검토한다. |
| 예약번호 생성 | `RSV-YYYYMMDD-0001` 같은 사용자 확인 가능한 번호를 생성한다. |
| 취소 정책 | 현재 시각과 예약 시각을 비교해 취소 가능 여부를 서버에서 검증한다. |
| 상태 전이 | RESERVED → CANCELED, CHECKED_IN, NO_SHOW, COMPLETED 전이를 명확히 제한한다. |
| 조회 최적화 | 내 예약 조회는 필요한 컬럼과 조인만 사용한다. |
| 프론트 UX | 예약 가능/마감/임박 상태를 화면에서 바로 구분할 수 있게 응답한다. |

### 포트폴리오 어필 포인트

- 예약 정원 초과와 중복 예약을 서버 정책으로 방지했다.
- 예약 취소 가능 시간, 상태 전이, 동시성 등 실제 운영에서 문제가 되는 지점을 고려했다.

## 5. Visit Context

### 만들어야 할 기능

- 예약자 체크인
- 현장 접수
- 직원 대리 접수
- 방문 이력 생성
- 체크인 후 대기번호 발급 연계

### 고도화 포인트

| 항목 | 내용 |
|---|---|
| 예약번호 체크인 | 예약번호로 예약 정보를 조회하고 체크인 가능 상태인지 검증한다. |
| 중복 체크인 방지 | 이미 체크인된 예약은 다시 체크인할 수 없게 한다. |
| 지각 처리 | 예약 시간 10분 초과 시 일반 대기열로 이동할 수 있게 정책화한다. |
| 현장 접수 최소 정보 | 의료정보는 저장하지 않고 이름, 연락처, 업무 유형 등 필요한 정보만 받는다. |
| 직원 대리 접수 | 고령층이나 전화 요청을 직원이 대신 접수할 수 있게 한다. |
| 트랜잭션 | Visit 생성과 QueueTicket 생성은 하나의 트랜잭션으로 묶는다. |

### 포트폴리오 어필 포인트

- 예약 이후 현장 운영 흐름까지 연결했다.
- 온라인 예약자와 현장 방문자를 하나의 방문/대기 흐름으로 통합했다.

## 6. Queue Context

### 만들어야 할 기능

- 대기번호 발급
- 업무 유형별 대기열 조회
- 다음 대기자 호출
- 처리 시작
- 처리 완료
- HOLD 처리
- 재호출

### 고도화 포인트

| 항목 | 내용 |
|---|---|
| 대기번호 생성 | 업무 유형별로 일자 기준 순번을 발급한다. |
| 호출 우선순위 | 예약 시간대 안에서는 예약자를 우선 호출한다. |
| 상태 전이 제한 | WAITING, CALLED, IN_PROGRESS, HOLD, COMPLETED 전이를 엄격히 제한한다. |
| 미응답 처리 | 호출 후 3분 미응답 시 HOLD로 변경하고 재호출 가능하게 한다. |
| 직원 화면 응답 | 대기열 화면에 필요한 대기번호, 이름 마스킹, 업무명, 상태, 대기시간을 함께 제공한다. |
| 처리 이력 | `service_processes`에 처리 시작/완료 시간과 담당 직원을 기록한다. |
| 대시보드 연계 | 호출, 시작, 완료 시간이 평균 대기시간 계산에 활용되도록 저장한다. |

### 포트폴리오 어필 포인트

- 대기열을 단순 목록이 아니라 상태 전이와 우선순위가 있는 운영 도메인으로 설계했다.
- 직원 업무 화면과 대시보드 통계까지 이어지는 데이터를 설계했다.

## 7. Dashboard/Congestion Context

### 만들어야 할 기능

- 오늘 방문자 수
- 현재 대기 인원
- 평균 대기시간
- 노쇼율
- 시간대별 방문자 수
- 업무별 평균 대기시간
- 예약/현장 방문 비율
- 사용자 현재 혼잡도

### 고도화 포인트

| 항목 | 내용 |
|---|---|
| 실시간 집계 | MVP에서는 배치보다 실시간 SQL 집계를 우선한다. |
| 인덱스 설계 | `checked_in_at`, `service_type_id`, `status` 기준 인덱스를 검토한다. |
| 혼잡도 기준 | 대기 인원과 예상 대기시간을 함께 사용해 LOW, NORMAL, HIGH를 계산한다. |
| 관리자/사용자 분리 | 관리자는 상세 지표, 사용자는 현재 혼잡도 중심으로 제공한다. |
| 확장성 | 트래픽이 늘면 일별/시간대별 집계 테이블로 전환할 수 있게 한다. |
| 시각화 친화 응답 | 차트에서 바로 쓸 수 있도록 label/value 또는 timeBucket 구조를 고려한다. |

### 포트폴리오 어필 포인트

- 예약과 대기 데이터를 운영 지표로 연결했다.
- 단순 CRUD를 넘어 데이터 기반 운영 개선을 보여줄 수 있다.

- 예약자 체크인
- 현장 접수
- 업무 유형별 대기열
- 호출
- 처리 시작
- 처리 완료

### 관리자 화면

- 업무 유형 관리

- 직원 관리

- 대시보드 요약

### 고도화 포인트

| 항목 | 내용 |
|---|---|
| UX-first 설계 | 화면 흐름을 먼저 검토해 API 응답 구조에 반영한다. |

| 상태 표시 | 공통코드 API로 상태명과 배지 색상을 매핑한다. |
| 직원 업무 효율 | 직원 화면은 클릭 수를 줄이고 대기열 상태가 한눈에 보이게 한다. |
| 에러 UX | 정원 초과, 취소 불가, 권한 없음 같은 상황을 사용자 친화적으로 안내한다. |

## 포트폴리오 작성 관점

포트폴리오에서는 아래 흐름으로 설명하면 좋다.

1. 문제 정의: 보건소 방문 대기와 직원 운영 부담
2. 사용자 구분: 시민, 보호자, 직원, 관리자
3. 핵심 흐름: 예약 → 체크인/현장 접수 → 대기 → 호출 → 완료 → 통계
4. 기술 선택: eGovFrame, Spring Boot, MyBatis, PostgreSQL, React
5. 설계 포인트: Bounded Context, 공통 응답, 공통코드, 상태 전이
6. 난이도 포인트: 예약 동시성, 대기 우선순위, 권한 분리, 대시보드 집계
7. UX 포인트: 화면 흐름에 맞춘 API, 직원 업무 효율, 고령층 접근성
8. 확장 포인트: 다중 보건소, 알림, 키오스크, 배치 통계, pgvector AI

가장 강하게 어필할 수 있는 문장:

```text
단순 예약 CRUD가 아니라, 보건소 방문 업무의 실제 흐름을 예약, 방문, 대기, 호출, 처리, 통계까지 하나의 운영 데이터 흐름으로 연결했습니다.
```
