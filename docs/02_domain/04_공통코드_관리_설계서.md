# 공통코드 관리 설계서

## 1. 문서 목적

본 문서는 `보건소 스마트 예약·대기 및 혼잡도 분석 시스템`에서 사용할 공통코드 관리 방식을 정의한다.

공통코드는 예약 상태, 대기 상태, 사용자 역할, 혼잡도처럼 여러 화면과 API에서 반복적으로 사용하는 코드값을 데이터베이스에 저장하고, 필요한 곳에서 조회하여 사용하는 방식이다.

이 문서는 코드 에이전트가 공통코드 관련 테이블, 엔티티, API, 캐시, 사용 규칙을 일관되게 구현하도록 돕기 위한 기준 문서이다.

---

## 2. 공통코드 도입 배경

### 2.1 문제 상황

공통코드를 사용하지 않고 각 코드값과 한글 표시명을 코드에 직접 작성하면 다음 문제가 생긴다.

| 문제 | 설명 |
|---|---|
| 중복 증가 | 예약 상태, 대기 상태 같은 값이 여러 클래스와 화면에 반복 작성된다. |
| 변경 어려움 | `예약 완료`라는 표시명을 바꾸려면 여러 파일을 수정해야 한다. |
| 화면 불일치 | 백엔드, 프론트엔드, 관리자 화면에서 같은 상태를 다르게 표시할 수 있다. |
| 운영 관리 어려움 | 표시 순서, 사용 여부, 설명 등을 운영 중 조정하기 어렵다. |
| 코드 가독성 저하 | 의미 없는 문자열 비교가 많아진다. |

### 2.2 도입 목적

| 목적 | 설명 |
|---|---|
| 코드값 표준화 | 시스템 전체에서 동일한 코드값을 사용한다. |
| 표시명 중앙 관리 | 코드명, 설명, 정렬 순서, 사용 여부를 DB에서 관리한다. |
| 프론트엔드 연동 | 화면의 셀렉트 박스, 상태 배지, 필터 목록을 공통코드 API로 구성한다. |
| 운영 편의성 | 사용 여부와 정렬 순서를 관리자 기능으로 조정할 수 있다. |
| 확장성 | 향후 여러 보건소나 업무 유형 확장 시 코드 관리 방식을 유지할 수 있다. |

## 3. 공통코드와 Enum의 관계

공통코드를 DB로 관리한다고 해서 모든 상태값을 문자열로만 처리하면 안 된다.  
도메인 로직에서 중요한 상태는 Java Enum으로도 관리해야 한다.

따라서 본 프로젝트는 다음과 같은 하이브리드 방식을 사용한다.

```text
도메인 로직의 안정성: Java Enum
화면 표시와 운영 관리: DB 공통코드
```

### 3.1 Enum으로 관리해야 하는 것

다음처럼 비즈니스 규칙과 상태 전이가 중요한 값은 Java Enum으로 관리한다.

| 값 | 이유 |
|---|---|
| ReservationStatus | 예약 완료, 취소, 체크인, 노쇼, 완료 등 상태 전이가 중요하다. |
| QueueStatus | 대기중, 호출됨, 처리중, 완료, 보류 등 상태 전이가 중요하다. |
| UserRole | 권한 검증과 보안에 직접 사용된다. |
| VisitType | 예약 방문, 현장 방문, 직원 대리 접수 로직에 사용된다. |
| CongestionLevel | 혼잡도 계산 결과로 사용된다. |

### 3.2 DB 공통코드로 관리해야 하는 것

다음 정보는 DB 공통코드로 관리한다.

| 값 | 이유 |
|---|---|
| 코드 표시명 | 화면에서 보여줄 한글명 관리 |
| 정렬 순서 | 셀렉트 박스, 필터 목록 표시 순서 관리 |
| 사용 여부 | 더 이상 사용하지 않는 코드를 비활성화 |
| 설명 | 관리자 화면이나 API 문서에서 의미 설명 |
| 시스템 코드 여부 | 사용자가 수정할 수 있는 코드와 수정 불가 코드를 구분 |

### 3.3 업무 유형은 공통코드가 아닌 기준정보로 관리

`예방접종`, `건강검진/검사`, `건강상담`은 공통코드처럼 보일 수 있지만, 본 프로젝트에서는 `service_types` 테이블로 관리한다.

이유는 다음과 같다.

| 구분 | 공통코드 | 업무 유형 |
|---|---|---|
| 사용 범위 | 시스템 전체 공통 상태값 | 보건소별 업무 설정 |
| 보건소별 차이 | 거의 없음 | 보건소마다 다를 수 있음 |
| 추가 속성 | 코드명, 설명, 정렬 정도 | 기본 정원, 업무 설명, 활성 여부, 보건소 ID 필요 |
| 테이블 | common_codes | service_types |

따라서 업무 유형은 공통코드가 아니라 `Office Context`의 기준정보로 본다.

## 4. 공통코드 설계 원칙

| 원칙 | 설명 |
|---|---|
| 코드값은 영어 대문자 스네이크 케이스 사용 | `RESERVED`, `CHECKED_IN`, `NO_SHOW` |
| 그룹 코드는 영어 대문자 스네이크 케이스 사용 | `RESERVATION_STATUS`, `QUEUE_STATUS` |
| 코드 표시명은 한글 사용 | `예약 완료`, `체크인 완료` |
| 도메인 상태는 Enum과 동일한 코드값 사용 | Enum name과 DB code를 일치시킨다. |
| 코드 조회는 캐시 우선 | 매 요청마다 DB를 조회하지 않는다. |
| 시스템 코드는 임의 삭제 금지 | 예약 상태, 대기 상태, 권한 코드는 삭제하지 않는다. |
| 비활성화로 대체 | 운영 중인 코드 삭제보다 `active=false`를 우선한다. |
| 화면 표시용으로만 남용 금지 | 핵심 로직은 Enum과 도메인 메서드로 처리한다. |

### 6.1 USER_ROLE

| 코드 | 코드명 | 설명 | 정렬 |
|---|---|---|---:|
| CITIZEN | 일반 시민 | 본인 예약 사용자 | 1 |
| GUARDIAN | 보호자 | 가족 또는 고령층 대리 예약 사용자 | 2 |

| ADMIN | 관리자 | 보건소 운영 관리자 | 4 |

### 6.2 RESERVATION_STATUS

| 코드 | 코드명 | 설명 | 정렬 |
|---|---|---|---:|
| RESERVED | 예약 완료 | 사용자가 예약을 완료한 상태 | 1 |

| HIGH | 혼잡 | 대기 인원 또는 예상 대기시간이 높은 상태 | 3 |

## 7. 테이블 설계

### 7.1 common_code_groups

공통코드 그룹을 저장한다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | BIGSERIAL | PK | 코드 그룹 ID |
| group_code | VARCHAR(50) | UNIQUE, NOT NULL | 코드 그룹 코드 |
| group_name | VARCHAR(100) | NOT NULL | 코드 그룹명 |
| description | TEXT | NULL | 설명 |
| system_group | BOOLEAN | NOT NULL | 시스템 그룹 여부 |
| active | BOOLEAN | NOT NULL | 사용 여부 |
| created_at | TIMESTAMP | NOT NULL | 생성일 |
| updated_at | TIMESTAMP | NULL | 수정일 |

### 7.2 common_codes

공통코드를 저장한다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | BIGSERIAL | PK | 코드 ID |
| group_id | BIGINT | FK, NOT NULL | 코드 그룹 ID |
| code | VARCHAR(50) | NOT NULL | 코드 |
| code_name | VARCHAR(100) | NOT NULL | 코드 표시명 |
| description | TEXT | NULL | 설명 |
| sort_order | INT | NOT NULL | 정렬 순서 |
| system_code | BOOLEAN | NOT NULL | 시스템 코드 여부 |
| active | BOOLEAN | NOT NULL | 사용 여부 |
| created_at | TIMESTAMP | NOT NULL | 생성일 |
| updated_at | TIMESTAMP | NULL | 수정일 |

권장 제약:

```sql
UNIQUE (group_id, code)
```

## 8. JPA 엔티티 설계 방향

### 8.1 CommonCodeGroup

```java
@Entity
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class CommonCodeGroup extends BaseEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String groupCode;

    private String groupName;

    private String description;

    private boolean systemGroup;

    private boolean active;

    public static CommonCodeGroup create(
        String groupCode,
        String groupName,
        String description,
        boolean systemGroup
    ) {
        CommonCodeGroup group = new CommonCodeGroup();
        group.groupCode = groupCode;
        group.groupName = groupName;
        group.description = description;
        group.systemGroup = systemGroup;
        group.active = true;
        return group;
    }

    public void updateDisplayInfo(String groupName, String description) {
        this.groupName = groupName;
        this.description = description;
    }

    public void deactivate() {
        this.active = false;
    }
}
```

### 8.2 CommonCode

```java
@Entity
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class CommonCode extends BaseEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private Long groupId;

    private String code;

    private String codeName;

    private String description;

    private int sortOrder;

    private boolean systemCode;

    private boolean active;

    public static CommonCode create(
        Long groupId,
        String code,
        String codeName,
        String description,
        int sortOrder,
        boolean systemCode
    ) {
        CommonCode commonCode = new CommonCode();
        commonCode.groupId = groupId;
        commonCode.code = code;
        commonCode.codeName = codeName;
        commonCode.description = description;
        commonCode.sortOrder = sortOrder;
        commonCode.systemCode = systemCode;
        commonCode.active = true;
        return commonCode;
    }

    public void updateDisplayInfo(
        String codeName,
        String description,
        int sortOrder
    ) {
        this.codeName = codeName;
        this.description = description;
        this.sortOrder = sortOrder;
    }

    public void deactivate() {
        this.active = false;
    }
}
```

주의:

- Entity에는 `@Setter`를 사용하지 않는다.
- 상태 변경은 의미 있는 도메인 메서드로 처리한다.
- JPA 엔티티 필드명과 DB 컬럼명은 가능한 한 일치시킨다.
- `groupId`는 단순 FK로 둘 수 있고, 필요하면 `@ManyToOne(fetch = LAZY)`로 변경할 수 있다.

## 9. API 설계

### 9.1 공통코드 그룹 목록 조회

| 항목 | 내용 |
|---|---|
| Method | GET |
| URL | /api/common-code-groups |
| 권한 | STAFF, ADMIN |

### 9.2 특정 그룹 코드 목록 조회

| 항목 | 내용 |
|---|---|
| Method | GET |
| URL | /api/common-codes/{groupCode} |
| 권한 | PUBLIC 또는 로그인 사용자 |

예시:

```http
GET /api/common-codes/RESERVATION_STATUS
```

응답:

```json
{
  "success": true,
  "data": [
    {
      "groupCode": "RESERVATION_STATUS",
      "code": "RESERVED",
      "codeName": "예약 완료",
      "description": "사용자가 예약을 완료한 상태",
      "sortOrder": 1
    }
  ],
  "error": null
}
```

### 9.3 여러 그룹 코드 한 번에 조회

프론트엔드 초기 화면 로딩 시 여러 그룹을 한 번에 조회할 수 있도록 제공한다.

| 항목 | 내용 |
|---|---|
| Method | GET |
| URL | /api/common-codes |
| Query | groupCodes=RESERVATION_STATUS,QUEUE_STATUS,CONGESTION_LEVEL |

응답:

```json
{
  "success": true,
  "data": {
    "RESERVATION_STATUS": [
      {
        "code": "RESERVED",
        "codeName": "예약 완료",
        "sortOrder": 1
      }
    ],
    "QUEUE_STATUS": [
      {
        "code": "WAITING",
        "codeName": "대기중",
        "sortOrder": 1
      }
    ]
  },
  "error": null
}
```

### 9.4 관리자 코드 수정 API

MVP에서는 조회 API만 먼저 구현하고, 관리자 수정 API는 후순위로 둔다.

| Method | URL | 설명 | 우선순위 |
|---|---|---|---|
| GET | /api/common-codes/{groupCode} | 코드 조회 | MVP |
| GET | /api/common-codes | 여러 그룹 코드 조회 | MVP |
| PATCH | /api/admin/common-codes/{codeId} | 코드 표시명, 설명, 정렬 수정 | 2차 |
| PATCH | /api/admin/common-codes/{codeId}/deactivate | 코드 비활성화 | 2차 |

## 10. 캐시 전략

공통코드는 자주 조회되지만 자주 변경되지 않는다.  
따라서 매 요청마다 DB를 조회하지 않고 캐시를 사용한다.

### 10.1 기본 전략

| 항목 | 전략 |
|---|---|
| 조회 빈도 | 높음 |
| 변경 빈도 | 낮음 |
| MVP 캐시 | 애플리케이션 메모리 캐시 또는 Spring Cache |
| 캐시 단위 | groupCode 기준 |
| 캐시 무효화 | 관리자 코드 수정 시 해당 그룹 캐시 삭제 |
| 2차 확장 | Redis 캐시 고려 |

### 10.2 시간 복잡도 관점

DB에서 매번 조회하면 일반적으로 다음 비용이 발생한다.

```text
O(log N) 또는 O(N) + 네트워크/DB I/O
```

캐시를 사용하면 다음처럼 개선할 수 있다.

```text
Map 기반 조회: 평균 O(1)
```

권장 캐시 구조:

```java
Map<String, List<CommonCodeResponse>>
```

또는 코드값 직접 조회가 많다면 다음 구조를 사용할 수 있다.

```java
Map<String, Map<String, CommonCodeResponse>>
```

### 10.3 공간 복잡도 관점

공통코드는 데이터 수가 적다.  
따라서 코드 전체를 메모리에 캐시해도 메모리 부담이 작다.

```text
공간 복잡도: O(G + C)
G = 코드 그룹 수
C = 코드 수
```

## 11. 트랜잭션 정책

| 기능 | 트랜잭션 |
|---|---|
| 공통코드 조회 | `@Transactional(readOnly = true)` |
| 공통코드 그룹 생성 | `@Transactional` |
| 공통코드 생성 | `@Transactional` |
| 공통코드 수정 | `@Transactional` |
| 공통코드 비활성화 | `@Transactional` |
| 캐시 조회 | 트랜잭션 불필요 또는 readOnly |

예시:

```java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class CommonCodeQueryService {

    private final CommonCodeRepository commonCodeRepository;

    public List<CommonCodeResponse> findActiveCodesByGroupCode(String groupCode) {
        return commonCodeRepository.findActiveCodesByGroupCode(groupCode)
            .stream()
            .map(CommonCodeResponse::from)
            .toList();
    }
}
```

수정 서비스는 별도로 분리한다.

```java
@Service
@RequiredArgsConstructor
public class CommonCodeCommandService {

    private final CommonCodeRepository commonCodeRepository;

    @Transactional
    public void updateCommonCode(Long codeId, CommonCodeUpdateRequest request) {
        CommonCode commonCode = commonCodeRepository.findById(codeId)
            .orElseThrow(() -> new CustomException(ErrorCode.COMMON_CODE_NOT_FOUND));

        commonCode.updateDisplayInfo(
            request.codeName(),
            request.description(),
            request.sortOrder()
        );
    }
}
```

## 16. 주의사항

1. 도메인 상태 전이를 DB 공통코드만 믿고 처리하지 않는다.
2. 예약 상태나 대기 상태 변경 가능 여부는 도메인 메서드에서 검증한다.
3. 공통코드는 화면 표시와 코드 목록 제공에 우선 사용한다.
4. 업무 유형은 공통코드가 아니라 `service_types` 기준정보로 관리한다.
5. 공통코드를 캐시하더라도 관리자 수정 시 캐시 무효화 전략을 고려한다.
6. 시스템 코드는 삭제하지 않고 비활성화한다.
7. 코드값 변경은 기존 데이터와 연결되므로 매우 신중하게 처리한다.
