# 배포 후 상태 확인과 문제 해결 가이드

## 1. 문서 목적

이 문서는 Jenkins 배포가 끝난 뒤 서비스가 제대로 떠 있는지 확인하고, Prometheus, Grafana, Loki, Promtail에서 문제가 보일 때 원인을 좁히는 절차를 정리한다.

대상은 Ubuntu VM 내부 Jenkins가 `docker compose --env-file .env --profile observability`로 애플리케이션과 운영 상태 확인 도구를 함께 배포하는 구조다.

관련 배경:

- Jenkins가 `observability` profile을 누락하면 Prometheus/Grafana/Loki/Promtail 컨테이너가 생성되지 않는다.
- Jenkins 컨테이너 workspace 파일을 Docker host bind mount source로 쓰면 설정 파일 mount 오류가 날 수 있다.
- 현재 구조는 Prometheus/Grafana/Loki/Promtail 설정 파일을 custom image에 포함하고, Promtail의 Docker log 수집용 host mount만 유지한다.

### 이 문서에서 쓰는 말

| 표현 | 쉽게 말하면 |
|---|---|
| `observability` profile | Docker Compose에서 Prometheus/Grafana/Loki/Promtail까지 같이 띄우는 옵션 이름 |
| Prometheus scrape | Prometheus가 backend 상태 숫자를 주기적으로 가져오는 것 |
| target | Prometheus가 상태 숫자를 가져오려고 바라보는 대상 |
| Grafana datasource | Grafana가 Prometheus나 Loki 데이터를 읽어오는 연결 정보 |
| bind mount | 컨테이너 안에서 VM host 파일이나 폴더를 그대로 보게 연결하는 것 |

---

## 2. 현재 기준 구조

| 구분 | 현재 기준 |
|---|---|
| 배포 방식 | Jenkins Pipeline에서 Docker Compose 실행 |
| Compose project | `health-center` |
| 상태 확인 도구 profile | `observability` |
| Jenkins profile 적용 | `Jenkinsfile`의 `COMPOSE_PROFILE_ARGS = '--profile observability'` |
| Prometheus 수집 대상 | `backend:8080/actuator/prometheus` |
| Prometheus 수집 허용 | `.env`의 `OBSERVABILITY_PROMETHEUS_SCRAPE_ENABLED=true` |
| Grafana port | 기본 `3001` |
| Loki port | 기본 `3100` |
| 설정 파일 주입 | 각 상태 확인 도구 custom image에 `COPY` |
| 유지하는 bind mount | Promtail Docker log 수집용 `/var/lib/docker/containers`, `/var/run/docker.sock` |

Jenkins 배포 대상은 Jenkins 컨테이너가 마운트한 `/var/run/docker.sock`의 Docker host다. Ubuntu VM 배포를 확인할 때는 Jenkins도 Ubuntu VM 내부 Docker Engine 위에서 실행되어야 한다.

## 3. 배포 전 확인

Jenkins Credentials `health-center-env-file`로 등록한 `.env`에 아래 값이 있는지 확인한다.

```env
OBSERVABILITY_PROMETHEUS_SCRAPE_ENABLED=true
PROMETHEUS_PORT=9090
GRAFANA_PORT=3001
GRAFANA_ADMIN_USER=admin
GRAFANA_ADMIN_PASSWORD=change-me
GRAFANA_ROOT_URL=http://localhost:3001
LOKI_PORT=3100
```

운영 공개 환경에서 메트릭 공개가 우려되면 `OBSERVABILITY_PROMETHEUS_SCRAPE_ENABLED=false`를 유지한다. 이 경우 상태 확인 도구 컨테이너는 실행될 수 있지만 Prometheus의 backend target은 인증 차단으로 실패할 수 있다.

Jenkins가 VM Docker host에 붙어 있는지 확인한다.

```bash
docker exec -it health-center-jenkins sh -lc "hostname && docker info --format '{{.Name}} / {{.OperatingSystem}}'"
```

확인 기준:

- 명령은 Ubuntu VM 터미널에서 실행한다.
- Docker host가 Ubuntu VM Docker Engine이어야 한다.
- Windows 로컬 Jenkins에서 실행하면 Windows 로컬 Docker에 배포된다.

## 4. Jenkins Pipeline 확인 순서

Jenkins UI에서 `Build Now` 또는 main merge 후 Pipeline을 확인한다.

| 단계 | 확인할 것 | 실패 시 우선 의심 |
|---|---|---|
| `Prepare Env` | `.env`가 credentials에서 workspace로 복사됨 | Jenkins Credentials 누락, ID 오타 |
| `Docker Compose Config` | observability 서비스가 config 출력에 포함됨 | `--profile observability` 누락 |
| `Docker Build` | backend/frontend와 상태 확인 도구 custom image build | Dockerfile 경로, image pull, network |
| `Deploy` | `up -d --remove-orphans` 성공 | port 충돌, volume 권한, Promtail mount 권한 |
| `ps` | 앱과 상태 확인 도구 컨테이너가 함께 표시됨 | profile 누락, 컨테이너 기동 실패 |

Jenkinsfile의 핵심 기준:

```text
COMPOSE_PROFILE_ARGS = '--profile observability'
docker compose --env-file .env ${COMPOSE_PROFILE_ARGS} config
docker compose --env-file .env ${COMPOSE_PROFILE_ARGS} build
docker compose --env-file .env ${COMPOSE_PROFILE_ARGS} up -d --remove-orphans
docker compose --env-file .env ${COMPOSE_PROFILE_ARGS} ps
```

## 5. VM 컨테이너 확인

Jenkins Pipeline 성공 후 Ubuntu VM에서 확인한다.

```bash
docker compose --env-file .env --profile observability ps
```

기대 컨테이너:

```text
health-center-postgres
health-center-backend
health-center-frontend
health-center-prometheus
health-center-grafana
health-center-loki
health-center-promtail
```

Prometheus/Grafana/Loki/Promtail 컨테이너만 빠져 있으면 profile 적용을 먼저 확인한다.

```bash
docker compose --env-file .env --profile observability config
```

`prometheus`, `grafana`, `loki`, `promtail` 서비스가 출력에 포함되어야 한다.

## 6. Prometheus 확인

브라우저에서 Prometheus에 접속한다.

```text
http://<ubuntu-vm-ip>:9090
```

NAT 포트 포워딩 환경이면 Windows 브라우저에서 아래 주소를 사용한다.

```text
http://localhost:9090
```

확인 순서:

1. `Status > Targets`로 이동
2. `health-center-backend` target 확인
3. 상태가 `UP`인지 확인
4. `Graph`에서 `http_server_requests_seconds_count` 조회

대표 기대 결과:

```text
health-center-backend target 상태가 UP이고, backend HTTP request metric이 조회된다.
```

자주 보는 실패:

| 증상 | 원인 후보 | 대응 |
|---|---|---|
| `health-center-backend` 대상이 없음 | Prometheus 설정 image가 오래됨, 상태 확인 도구 image rebuild 누락 | Jenkins `Docker Build` 단계 재실행 |
| 대상이 DOWN | backend 미기동, Docker network 문제, Prometheus 수집 endpoint 인증 차단 | backend 컨테이너 상태와 `.env`의 `OBSERVABILITY_PROMETHEUS_SCRAPE_ENABLED=true` 확인 |
| 401/403 | Prometheus 수집 허용 값이 false | `.env`와 Jenkins Credentials 값을 true로 갱신 후 재배포 |
| connection refused | backend 컨테이너가 8080에서 떠 있지 않음 | `docker compose ps`, backend logs 확인 |

## 7. Grafana 확인

브라우저에서 Grafana에 접속한다.

```text
http://<ubuntu-vm-ip>:3001
```

로그인 계정은 `.env`의 값을 사용한다.

```env
GRAFANA_ADMIN_USER=admin
GRAFANA_ADMIN_PASSWORD=change-me
```

확인 순서:

1. `Connections > Data sources`에서 Prometheus와 Loki datasource 확인
2. `Dashboards`에서 `Health Center Backend Overview` 확인
3. HTTP request rate, 평균 latency, JVM heap 패널 확인
4. Backend error log 패널이 오류 없이 표시되는지 확인

자주 보는 실패:

| 증상 | 원인 후보 | 대응 |
|---|---|---|
| 로그인 실패 | Jenkins Credentials `.env`의 Grafana 계정 값과 다름 | `.env` 원본과 Jenkins Credentials 파일 확인 |
| datasource 없음 | Grafana image build가 오래됨, provisioning COPY 누락 | Jenkins build 재실행, `infra/observability/grafana/Dockerfile` 확인 |
| dashboard 없음 | dashboard provider path 불일치 | `/etc/grafana/dashboards` 기준인지 확인 |
| 패널이 `No data` | Prometheus 수집 대상 DOWN 또는 아직 트래픽 없음 | Prometheus target 확인 후 Swagger/브라우저로 API 요청 발생 |

---

## 8. Loki와 Promtail 확인

Loki는 Grafana datasource를 통해 확인하는 것을 우선한다.

Grafana Explore에서 datasource를 Loki로 선택하고 아래 label을 확인한다.

```logql
{service="backend"}
```

서비스 label이 다르게 보이면 Promtail Docker discovery label을 기준으로 조회한다.

```logql
{compose_project="health-center"}
```

자주 보는 실패:

| 증상 | 원인 후보 | 대응 |
|---|---|---|
| Loki datasource 연결 실패 | Loki 컨테이너 미기동, network 문제 | `docker compose --profile observability ps`, Loki logs 확인 |
| 로그가 없음 | Promtail 권한 또는 Docker log path mount 문제 | Promtail mount와 VM Docker 경로 확인 |
| Promtail 컨테이너 재시작 반복 | `/var/lib/docker/containers` 또는 docker.sock 접근 실패 | VM Docker 권한과 mount 경로 확인 |
| backend error log 패널만 비어 있음 | 최근 오류 로그가 없음 | 정상일 수 있음. 테스트용 Bad request를 Swagger에서 1회 발생시킨 뒤 재확인 |

현재 유지하는 Promtail host mount:

```yaml
- /var/lib/docker/containers:/var/lib/docker/containers:ro
- /var/run/docker.sock:/var/run/docker.sock:ro
```

이 mount는 Jenkins workspace 설정 파일 mount와 다르다. Docker log discovery와 container log file read를 위한 VM host runtime mount다.

## 9. 증상별 빠른 판단표

| 증상 | 가장 먼저 볼 곳 | 판단 |
|---|---|---|
| Jenkins 성공인데 Prometheus/Grafana/Loki/Promtail 컨테이너가 없음 | Jenkins `Docker Compose Config` 로그 | `--profile observability` 누락 가능성 |
| `prometheus.yml` mount 오류 | `docker-compose.yml`의 Prometheus/Grafana/Loki/Promtail volumes | 설정 파일 bind mount가 다시 들어갔는지 확인 |
| Prometheus 수집 대상 401/403 | Jenkins Credentials `.env` | `OBSERVABILITY_PROMETHEUS_SCRAPE_ENABLED` 값 확인 |
| Grafana dashboard 없음 | Grafana image와 provisioning path | image rebuild와 `/etc/grafana/dashboards` 경로 확인 |
| Loki 로그 없음 | Promtail logs와 mount | Docker socket/container log path 권한 확인 |
| Windows 브라우저 접속 실패 | VM 네트워크 방식 | NAT 포트 포워딩 또는 VM IP 기준 URL 확인 |

## 10. bind mount 오류 재발 시 확인

아래 형태의 오류가 다시 나오면 설정 파일 bind mount가 되살아났는지 확인한다.

```text
error mounting ".../infra/observability/prometheus/prometheus.yml"
to rootfs at "/etc/prometheus/prometheus.yml": not a directory
```

현재 의도한 구조:

- Prometheus 설정은 `infra/observability/prometheus/Dockerfile`에서 image에 포함
- Grafana datasource/dashboard는 `infra/observability/grafana/Dockerfile`에서 image에 포함
- Loki 설정은 `infra/observability/loki/Dockerfile`에서 image에 포함
- Promtail 설정은 `infra/observability/promtail/Dockerfile`에서 image에 포함
- Compose에는 설정 파일 bind mount를 두지 않음

확인 명령:

```bash
docker compose --env-file .env --profile observability config
```

Prometheus/Grafana/Loki/Promtail 서비스에 아래 같은 설정 파일 mount가 보이면 현재 기준과 다르다.

```text
./infra/observability/prometheus/prometheus.yml:/etc/prometheus/prometheus.yml
```

Promtail의 Docker log 수집용 host mount는 정상이다.

## 11. 포트폴리오 설명 포인트

면접 또는 포트폴리오에서는 아래 흐름으로 설명한다.

1. Actuator/Micrometer로 backend health, info, metrics, prometheus endpoint를 구성했다.
2. 보안상 `/actuator/prometheus`는 기본 보호 상태로 두고, 내부 상태 확인 도구에서만 환경변수로 Prometheus 수집을 허용했다.
3. Docker Compose profile로 Prometheus/Grafana/Loki/Promtail을 앱 실행과 분리했다.
4. Jenkins 배포에서 profile 누락으로 Prometheus/Grafana/Loki/Promtail 컨테이너가 생성되지 않는 문제를 Jenkinsfile에 `--profile observability`를 적용해 해결했다.
5. Jenkins 컨테이너 workspace와 Docker host bind mount 경로가 달라 설정 파일 mount 오류가 발생할 수 있어, Prometheus/Grafana/Loki/Promtail 설정을 custom image에 포함하는 구조로 바꿨다.
6. Grafana dashboard에서 API latency, request count, JVM 지표, backend error logs를 함께 확인할 수 있게 했다.

---

## 12. 운영 주의사항

- Grafana, Prometheus, Loki는 외부 공개 대상이 아니다.
- Cloudflare Tunnel public hostname은 frontend/backend 시연 주소 중심으로 만든다.
- Jenkins Credentials의 `.env`는 Git에 올리지 않는다.
- Prometheus/Grafana/Loki/Promtail 설정 파일을 수정하면 Jenkins Pipeline의 build 단계를 다시 실행해야 image에 반영된다.
- VM마다 Prometheus target, Grafana root URL, retention 정책이 달라지면 환경별 설정 외부화를 후속으로 검토한다.
