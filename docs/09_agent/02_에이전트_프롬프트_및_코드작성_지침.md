# 코드 에이전트 프롬프트 및 코드 작성 지침

## 1. 문서 목적

본 문서는 `보건소 스마트 예약·대기 및 혼잡도 분석 시스템`에서 코드 에이전트가 코드를 작성할 때 반드시 따라야 할 지침을 정의한다.

이 문서는 단순한 코딩 컨벤션이 아니라, 에이전트에게 어떻게 요청하고, 에이전트가 어떤 기준으로 코드를 작성하고, 작업 후 어떤 결과물을 제공해야 하는지를 안내하는 프롬프트 운영 문서이다.

---

## 2. 에이전트 기본 페르소나

코드 에이전트는 항상 다음 역할로 동작한다.

```text
당신은 공공 SI, 전자정부프레임워크, Spring Boot, JPA, PostgreSQL, React 기반 시스템 개발 경험이 풍부한 시니어 IT 개발자입니다.

당신은 단순히 동작하는 코드를 작성하는 것이 아니라, 유지보수 가능한 구조, 명확한 이름, 적절한 트랜잭션, 예외 처리, 성능, 테스트 가능성을 함께 고려해야 합니다.
```

---

## 3. 적용 우선순위

에이전트는 아래 순서로 규칙을 적용한다.

1. 사용자의 현재 지시
2. 이 문서
3. `code_convention.md`
4. 기존 프로젝트 코드 패턴
5. 일반적인 Spring Boot/JPA 모범 사례

충돌이 발생하면 사용자에게 확인하거나, 명확히 판단 가능한 경우 이 문서의 규칙을 우선 적용한다.

---

### 3.1 작업 전 GitNexus 준비 원칙

에이전트는 코드 구현, 리팩토링, 디버깅, 영향도 분석처럼 코드 구조 이해가 필요한 작업을 시작하기 전에 GitNexus 사용 가능 상태를 확인한다.

기본 절차:

1. 프로젝트 루트에서 `npx gitnexus status`를 실행한다.
2. 인덱스가 없거나 오래된 경우 `npx gitnexus analyze`를 실행한다.
3. 분석 완료 후 GitNexus 컨텍스트나 관련 탐색 기능을 사용할 수 있으면 우선 활용한다.
4. 대규모 코드 변경 후에는 필요 시 `npx gitnexus analyze`로 인덱스를 갱신한다.

제한사항:

- `--embeddings` 옵션은 사용자가 의미 검색 또는 임베딩 검색을 명시한 경우에만 사용한다.
- GitNexus 실행 실패가 작업 전체의 중단 사유는 아니다. 실패 이유를 보고하고 일반 파일 탐색과 테스트 기반으로 진행한다.
- 문서 수정, 설정 파일 단순 변경처럼 코드 구조 분석이 필요 없는 작업에서는 생략할 수 있다.
- 실제 커밋은 하지 않고, 필요한 경우 커밋 메시지 초안만 제공한다.

## 4. POWER 원칙 기반 프롬프트 작성법

작업 요청은 가능하면 POWER 원칙 중 2~3가지 이상을 포함한다.

| 항목 | 의미 | 작성 예시 |
|---|---|---|
| Persona | 역할 부여 | 공공 SI 경험이 많은 시니어 백엔드 개발자로 작업해주세요. |
| Outcome | 원하는 결과물 | 예약 신청 API와 관련 엔티티, 서비스, 컨트롤러를 구현해주세요. |
| Why | 이유 | 예약 정원 초과와 중복 예약을 방지해야 하기 때문입니다. |
| Example | 예시 | 응답 형식은 ApiResponse.success(data) 형태로 맞춰주세요. |
| Restriction | 제한사항 | Entity에 Setter를 만들지 말고, 트랜잭션 경계를 지켜주세요. |

## 5. 좋은 프롬프트 작성 원칙

### 5.1 명확하고 구체적으로 지시

나쁜 예:

```text
예약 기능 만들어줘.
```

좋은 예:

```text
예약 기능을 구현해주세요.

범위:
- Reservation 엔티티
- ReservationSlot 엔티티
- 예약 가능 시간 조회 API
- 예약 신청 API
- 내 예약 조회 API
- 예약 취소 API

정책:
- 예약 단위는 30분입니다.
- 예약 가능 기간은 오늘부터 14일입니다.
- 예약 취소는 방문 1시간 전까지 가능합니다.
- 예약 슬롯 정원을 초과하면 예외를 던져야 합니다.
```

### 5.2 충분한 배경 정보 제공

작업 대상이 어떤 프로젝트인지 항상 알려준다.

```text
이 프로젝트는 보건소의 예약, 현장 접수, 대기번호, 직원 호출, 혼잡도 대시보드를 제공하는 시스템입니다.
MVP는 단일 보건소 기준이지만 DB 구조는 다중 보건소 확장을 고려합니다.
```

### 5.3 샘플 예시 제공

스타일이 중요한 경우 반드시 예시를 제공한다.

```text
커밋 메시지는 다음 형식으로 제안해주세요.

feat: 예약 신청 기능 구현

- 예약 가능 슬롯 조회 로직 추가
- 예약 정원 초과 검증 추가
- 동일 시간대 중복 예약 방지
```

### 5.4 큰 일을 작은 단위로 분리

한 번에 전체 시스템을 만들지 않는다.

권장 작업 단위:

1. 공통 응답/예외
2. 인증/권한
3. 공통코드
4. 업무 유형/예약 슬롯
5. 예약
6. 체크인/현장 접수
7. 대기열/호출
8. 대시보드
9. 프론트 화면
10. 테스트

### 5.5 대화하면서 발전

첫 결과물은 완성품이 아니다.  
에이전트가 만든 결과물을 보고 다음 기준으로 개선 요청한다.

| 확인 항목 | 질문 |
|---|---|
| 이름 | 이름만 보고 역할이 드러나는가? |
| 책임 | 한 클래스가 너무 많은 일을 하지 않는가? |
| 트랜잭션 | 읽기와 쓰기 트랜잭션이 분리되었는가? |
| 예외 | 실패 상황이 구체적으로 표현되는가? |
| 성능 | 불필요한 반복 조회나 N+1 문제가 없는가? |
| 테스트 | 해피 케이스만 고려하지 않았는가? |

## 6. 코드 작성 핵심 원칙

### 6.1 이름 명명

이름은 가장 중요하다.  
클래스명, 메서드명, 변수명만 봐도 역할을 알 수 있어야 한다.

#### 클래스명

| 대상 | 규칙 | 예시 |
|---|---|---|
| Controller | `~Controller` | `ReservationController` |
| Service | `~Service` | `ReservationCommandService` |
| 조회 Service | `~QueryService` | `ReservationQueryService` |
| 변경 Service | `~CommandService` | `ReservationCommandService` |
| Repository | `~Repository` | `ReservationRepository` |
| Request DTO | `~Request` | `ReservationCreateRequest` |
| Response DTO | `~Response` | `ReservationResponse` |
| Exception | `~Exception` | `ReservationNotFoundException` |

#### 메서드명

| 목적 | 접두어 | 예시 |
|---|---|---|
| 생성 | create | `createReservation()` |
| 조회 | find, get | `findMyReservations()` |
| 검증 | validate, check | `validateSlotCapacity()` |
| 취소 | cancel | `cancelReservation()` |
| 호출 | call | `callQueueTicket()` |
| 완료 | complete | `completeServiceProcess()` |
| 상태 변경 | 의미 있는 동사 | `markAsCheckedIn()`, `moveToHold()` |

금지:

- 의미 없는 축약어
- 역할이 모호한 `process()`, `handle()`, `doSomething()`
- 문자열 상태 변경만 드러나는 `setStatus()`
- 한 글자 변수명

---

### 6.2 공간·시간 복잡도 고려

기능 구현 시 항상 다음을 확인한다.

| 확인 항목 | 설명 |
|---|---|
| 반복문 안 DB 조회 금지 | N+1 문제와 성능 저하를 유발한다. |
| 필요한 데이터만 조회 | 전체 엔티티 목록을 가져와 메모리에서 필터링하지 않는다. |
| 조회 전용 API 최적화 | DTO Projection, fetch join, query 최적화를 고려한다. |
| 공통코드 캐시 | 공통코드는 매 요청마다 DB 조회하지 않는다. |
| 대시보드 쿼리 최적화 | 통계 조회는 DB 집계 쿼리를 우선 고려한다. |
| 컬렉션 선택 | 검색이 많으면 List보다 Map 또는 Set을 고려한다. |

예시:

```text
대기번호 ID로 상태명을 자주 찾는 경우
List 순회: O(N)
Map 조회: 평균 O(1)
```

### 6.3 트랜잭션 설계

트랜잭션은 매우 중요하다.  
에이전트는 서비스 메서드 작성 시 항상 트랜잭션 경계를 명시해야 한다.

#### 기본 원칙

| 상황 | 권장 |
|---|---|
| 조회 전용 서비스 | `@Transactional(readOnly = true)` |
| 생성/수정/삭제 | `@Transactional` |
| 여러 엔티티 상태가 함께 변경되는 기능 | 하나의 트랜잭션으로 묶기 |
| 외부 API 호출 | DB 트랜잭션 안에서 오래 대기하지 않도록 분리 |
| 대시보드 조회 | readOnly 트랜잭션 또는 별도 조회 서비스 |

#### 예시

예약 신청은 다음 작업이 함께 처리되어야 한다.

```text
1. 예약 슬롯 조회
2. 예약 가능 여부 검증
3. 예약 인원 증가
4. 예약 생성
```

따라서 하나의 쓰기 트랜잭션으로 묶는다.

```java
@Transactional
public ReservationCreateResponse createReservation(
    Long memberId,
    ReservationCreateRequest request
) {
    ReservationSlot slot = reservationSlotRepository.findByIdForUpdate(request.reservationSlotId())
        .orElseThrow(() -> new CustomException(ErrorCode.RESERVATION_SLOT_NOT_FOUND));

    slot.reserve();

    Reservation reservation = Reservation.create(
        memberId,
        request.serviceTypeId(),
        slot.getId()
    );

    Reservation savedReservation = reservationRepository.save(reservation);

    return ReservationCreateResponse.from(savedReservation);
}
```

예약 가능 시간 조회는 readOnly로 처리한다.

```java
@Transactional(readOnly = true)
public List<ReservationSlotResponse> findAvailableSlots(
    Long serviceTypeId,
    LocalDate date
) {
    return reservationSlotRepository.findActiveSlots(serviceTypeId, date)
        .stream()
        .map(ReservationSlotResponse::from)
        .toList();
}
```

### 6.4 객체지향 설계

서비스 레이어가 두꺼워지지 않게 한다.  
상태 변경 규칙은 가능한 한 도메인 객체 내부에 둔다.

나쁜 예:

```java
reservation.setStatus(ReservationStatus.CANCELED);
```

좋은 예:

```java
reservation.cancel(now);
```

나쁜 예:

```java
queueTicket.setStatus(QueueStatus.COMPLETED);
queueTicket.setCompletedAt(LocalDateTime.now());
```

좋은 예:

```java
queueTicket.complete(now);
```

#### 도메인 메서드 예시

```java
public void cancel(LocalDateTime now) {
    if (!this.status.canCancel()) {
        throw new CustomException(ErrorCode.RESERVATION_CANNOT_CANCEL);
    }

    if (this.reservedAt.isBefore(now.plusHours(1))) {
        throw new CustomException(ErrorCode.RESERVATION_CANCEL_TIME_EXPIRED);
    }

    this.status = ReservationStatus.CANCELED;
    this.canceledAt = now;
}
```

서비스가 커지면 다음 기준으로 분리한다.

| 분리 기준 | 예시 |
|---|---|
| 조회/변경 분리 | `ReservationQueryService`, `ReservationCommandService` |
| 관리자/사용자 분리 | `AdminReservationService`, `ReservationService` |
| 정책 분리 | `ReservationPolicy`, `QueuePriorityPolicy` |
| 계산 분리 | `CongestionCalculator`, `WaitTimeEstimator` |
| 외부 연동 분리 | `NotificationSender` |

### 6.6 예외 처리

예외 구조는 다음 패턴을 따른다.

```text
ErrorCode + CustomException + GlobalExceptionHandler
```

예외 메시지는 한글로 작성하되, 코드값은 영어 대문자 스네이크 케이스를 사용한다.

예시:

```java
throw new CustomException(ErrorCode.RESERVATION_SLOT_FULL);
```

예외 코드 예시:

| ErrorCode | 메시지 |
|---|---|
| RESERVATION_NOT_FOUND | 예약 정보를 찾을 수 없습니다. |
| RESERVATION_SLOT_FULL | 선택한 시간대의 예약이 마감되었습니다. |
| RESERVATION_DUPLICATED | 동일 시간대에 이미 예약이 존재합니다. |
| QUEUE_TICKET_NOT_FOUND | 대기번호 정보를 찾을 수 없습니다. |
| QUEUE_INVALID_STATUS | 현재 대기 상태에서는 요청을 처리할 수 없습니다. |

## 7. JPA 작성 지침

### 7.1 Entity

| 규칙 | 설명 |
|---|---|
| `@Setter` 금지 | 도메인 메서드로 상태 변경 |
| `@NoArgsConstructor(access = PROTECTED)` 사용 | JPA 기본 생성자 보호 |
| 생성자 또는 정적 팩토리 메서드 사용 | 객체 생성 의도 명확화 |
| Entity를 Controller 응답으로 직접 노출 금지 | Response DTO로 변환 |
| 필드명과 컬럼명은 가능한 일치 | 불필요한 매핑 혼란 방지 |
| 상태값은 `@Enumerated(EnumType.STRING)` | ordinal 저장 금지 |

### 7.2 Repository

| 규칙 | 설명 |
|---|---|
| 단건 조회는 Optional 반환 | `orElseThrow()` 사용 |
| 복수 조회는 빈 리스트 반환 | null 반환 금지 |
| 복잡한 통계는 JPQL 또는 Native Query 고려 | 대시보드 성능 |
| 예약 정원 증가처럼 동시성 이슈가 있는 조회는 Lock 고려 | `@Lock(PESSIMISTIC_WRITE)` 또는 낙관적 락 검토 |

### 7.3 DTO

| 규칙 | 설명 |
|---|---|
| Request/Response는 record 사용 권장 | Java 17 기준 |
| Request DTO에 Bean Validation 사용 | `@NotNull`, `@NotBlank` 등 |
| Response DTO에 `from()` 정적 메서드 사용 | 변환 위치 일관화 |
| 내부 Command DTO는 필요할 때만 사용 | Controller와 Service 경계 분리 |

## 8. 테스트 코드 지침

### 8.1 기본 방향

테스트 코드는 기능 구현의 마지막 단계에서 작성한다.  
단, 에이전트는 기능 구현 시점부터 테스트 케이스 후보를 함께 생각해야 한다.

MVP 구현 초반에는 다음을 우선한다.

1. 빌드 가능 상태 유지
2. 핵심 흐름 수동 검증 가능
3. Swagger 또는 API 클라이언트로 확인 가능
4. 기능 단위가 안정되면 테스트 코드 작성

### 8.2 테스트는 해피 케이스만 작성하지 않는다

테스트 케이스는 다음 3가지를 포함한다.

| 유형 | 설명 |
|---|---|
| Happy Case | 정상적으로 성공하는 경우 |
| Edge Case | 경계값, 시간 제한, 정원 제한 등 |
| Bad Case | 잘못된 요청, 권한 없음, 존재하지 않는 데이터 등 |

### 8.3 테스트 후보 예시

#### 예약 신청 테스트

| 유형 | 케이스 |
|---|---|
| Happy | 예약 가능한 슬롯에 예약하면 RESERVED 상태가 된다. |
| Edge | 슬롯 정원이 정확히 마지막 1자리일 때 예약이 성공한다. |
| Edge | 방문 1시간 전에는 취소가 가능하다. |
| Bad | 정원이 가득 찬 슬롯에 예약하면 예외가 발생한다. |
| Bad | 동일 사용자가 같은 시간대에 중복 예약하면 예외가 발생한다. |
| Bad | 14일 이후 날짜에 예약하면 예외가 발생한다. |

#### 체크인 테스트

| 유형 | 케이스 |
|---|---|
| Happy | 예약번호로 체크인하면 Visit과 QueueTicket이 생성된다. |
| Edge | 예약 시간 10분 이내 지각은 예약자 대기열로 들어간다. |
| Edge | 예약 시간 10분 초과 지각은 일반 대기열로 이동한다. |
| Bad | 존재하지 않는 예약번호로 체크인하면 예외가 발생한다. |
| Bad | 이미 체크인한 예약을 다시 체크인하면 예외가 발생한다. |

#### 대기 호출 테스트

| 유형 | 케이스 |
|---|---|
| Happy | WAITING 상태 대기자를 호출하면 CALLED 상태가 된다. |
| Happy | CALLED 상태 대기자를 처리 시작하면 IN_PROGRESS 상태가 된다. |
| Happy | IN_PROGRESS 상태 대기자를 완료하면 COMPLETED 상태가 된다. |
| Edge | 호출 후 3분 미응답이면 HOLD 상태가 된다. |
| Bad | COMPLETED 상태 대기자를 다시 호출하면 예외가 발생한다. |
| Bad | 권한 없는 사용자가 호출 API를 실행하면 403이 발생한다. |

## 9. 커밋 메시지 지침

### 9.1 기본 원칙

- 에이전트는 실제 커밋을 하지 않는다.
- 사용자가 바로 사용할 수 있도록 커밋 메시지 초안을 제공한다.
- 커밋 제목과 본문은 한글로 작성한다.
- 제목 앞에는 prefix를 붙인다.
- 제목에는 모듈명을 넣지 않는다.
- 변경 단위가 여러 개면 커밋 메시지도 나누어 제안한다.

### 9.2 prefix 목록

| Prefix | 의미 |
|---|---|
| feat | 기능 추가 |
| fix | 오류 수정 |
| refactor | 구조 개선 |
| docs | 문서 추가/수정 |
| test | 테스트 추가/수정 |
| chore | 설정, 빌드, 기타 작업 |
| style | 포맷팅, 코드 스타일 |
| perf | 성능 개선 |

### 9.3 좋은 예시

```text
feat: 예약 신청 기능 구현

- 예약 완료 응답 DTO 추가
```



## 12. 코드 리뷰 체크리스트

에이전트가 코드를 작성한 후 사용자는 다음 기준으로 확인한다.

### 12.1 이름

- 클래스명만 보고 역할을 알 수 있는가?
- 메서드명이 동사로 시작하고 행위를 명확히 표현하는가?
- 변수명이 축약어 없이 의미를 드러내는가?

### 12.2 구조

- Controller는 요청/응답 처리만 담당하는가?
- Service는 유스케이스를 조합하는 수준인가?
- 도메인 상태 변경이 Entity 메서드로 들어갔는가?
- Repository는 데이터 접근만 담당하는가?

### 12.3 트랜잭션

- 조회 메서드에 `readOnly = true`가 적용되었는가?
- 쓰기 메서드에 `@Transactional`이 적용되었는가?
- 예약 생성처럼 여러 데이터가 함께 변경되는 작업이 하나의 트랜잭션으로 묶였는가?

### 12.4 성능

- 반복문 안에서 Repository 호출이 없는가?
- 대시보드 통계가 불필요하게 전체 데이터를 메모리에 올리지 않는가?
- 공통코드를 매번 DB에서 조회하지 않는가?
- N+1 가능성이 있는 조회에 fetch join 또는 DTO 조회를 고려했는가?

### 12.5 예외

- 실패 상황마다 ErrorCode가 있는가?
- 예외 메시지가 한글로 구체적인가?
- 예외를 삼키지 않는가?
- 민감 정보가 로그나 예외 메시지에 노출되지 않는가?

### 12.6 테스트 후보

- 해피 케이스가 있는가?
- 엣지 케이스가 있는가?
- 베드 케이스가 있는가?
- 권한 실패 케이스가 있는가?
