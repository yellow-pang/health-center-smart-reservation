# 포트폴리오 구현 스토리라인

## 문서 목적

이 문서는 보건소 스마트 예약·대기 및 혼잡도 분석 시스템을 포트폴리오에서 어떻게 설명할지 정리한다.

이미 기획서, 요구사항, API, ERD, 화면 설계서는 존재하므로 이 문서에서는 내용을 반복하지 않는다. 대신 면접관이나 검토자가 프로젝트의 의도, 기술적 판단, 구현 난이도, 확장 가능성을 빠르게 이해할 수 있도록 이야기 흐름을 정리한다.

## 한 줄 소개

```text
보건소 방문 업무의 예약, 현장 접수, 대기번호, 직원 호출, 처리 완료, 혼잡도 분석을 하나의 흐름으로 연결한 공공보건 운영 지원 시스템입니다.
```

## 문제 정의

기존 보건소 방문 업무는 온라인 예약, 현장 접수, 대기 관리, 운영 통계가 분리되어 있는 경우가 많다.

이로 인해 다음 문제가 발생한다.

| 사용자 | 문제 |
|---|---|
| 시민 | 방문 전 대기 상황을 알기 어렵다. |
| 보호자 | 고령층이나 가족을 대신해 예약하기 어렵다. |
| 직원 | 예약자와 현장 방문자를 함께 관리하기 어렵다. |
| 관리자 | 언제 어떤 업무가 혼잡한지 데이터로 파악하기 어렵다. |

## 해결 방향

이 프로젝트는 예약에서 끝나는 시스템이 아니라 방문 이후 흐름까지 연결한다.

```text
예약
→ 체크인 또는 현장 접수
→ 대기번호 발급
→ 직원 호출
→ 처리 시작
→ 처리 완료
→ 대시보드 통계 반영
```

핵심 차별점:

- 온라인 예약자와 현장 방문자를 하나의 대기 흐름으로 통합
- 직원이 현장에서 처리할 수 있는 운영 화면 제공
- 관리자에게 방문자 수, 대기시간, 노쇼율 같은 지표 제공
- 사용자에게 현재 혼잡도 제공

## 기술 선택 설명

| 기술 | 선택 이유 |
|---|---|
| eGovFrame Simple Backend Template | 공공 SI 맥락과 전자정부프레임워크 경험을 보여주기 좋음 |
| Spring Boot REST API | React 프론트엔드와 분리된 API 서버 구성 |
| Maven | eGovFrame 템플릿 구조 유지 |
| MyBatis | 통계 쿼리와 명시적 SQL 제어에 적합 |
| PostgreSQL 18 | 관계형 데이터와 확장성을 함께 고려 |
| pgvector 이미지 | MVP에서는 쓰지 않지만 향후 AI 검색 확장 여지 확보 |
| React | 사용자, 직원, 관리자 화면을 분리해 구현하기 적합 |
| Docker Compose | 포트폴리오 시연 환경 재현성 확보 |

## 설계 포인트

### Bounded Context

도메인을 아래 Context로 분리한다.

| Context | 책임 |
|---|---|
| Common | 공통 응답, 공통코드, 예외 |
| Office | 보건소, 업무 유형, 창구 |
| Auth/Member | 로그인, 사용자, 권한 |
| Reservation | 예약 슬롯, 예약 신청, 취소 |
| Visit | 체크인, 현장 접수 |
| Queue | 대기번호, 호출, 처리 상태 |
| Dashboard | 통계, 혼잡도 |

어필 포인트:

```text
처음부터 MSA로 과설계하지 않고, 모듈형 단일 애플리케이션 안에서 Bounded Context 기준으로 책임을 나눴습니다.
```

### 공통코드와 Enum 분리

도메인 상태값은 Java Enum으로 안정성을 확보하고, 화면 표시명과 정렬은 DB 공통코드로 관리한다.

어필 포인트:

```text
상태 전이처럼 중요한 비즈니스 규칙은 코드에서 통제하고, 화면 표시명은 DB 공통코드로 관리해 운영 유연성을 확보했습니다.
```

### UX/API 계약 중심 개발

화면 흐름을 먼저 확인하고 필요한 API 응답을 정의한다.

어필 포인트:

```text
백엔드 API를 단순 엔티티 반환이 아니라 실제 화면에서 필요한 업무 흐름 기준으로 설계했습니다.
```

## 기술적 난이도 포인트

### 예약 동시성

문제:

- 마지막 1자리에 여러 사용자가 동시에 예약할 수 있다.

대응:

- 조건부 update 또는 row lock으로 `reserved_count < capacity` 조건을 보장한다.
- 예약 생성과 슬롯 인원 증가는 하나의 트랜잭션으로 묶는다.

### 상태 전이

문제:

- 예약, 방문, 대기 상태는 잘못 변경되면 운영 데이터가 깨진다.

대응:

- 상태 변경은 Service와 Policy에서 검증한다.
- 단순 문자열 update를 피하고 의미 있는 메서드로 처리한다.

### 대기 우선순위

문제:

- 예약자와 현장 방문자를 같은 대기열에서 관리해야 한다.

대응:

- 예약 시간대 안에서는 예약자를 우선 호출한다.
- 지각자는 정책에 따라 일반 대기열로 이동할 수 있게 한다.

### 대시보드 집계

문제:

- 통계는 여러 테이블의 시간 데이터를 기반으로 계산해야 한다.

대응:

- MVP에서는 실시간 SQL 집계로 시작한다.
- 이후 성능 문제가 생기면 집계 테이블과 배치로 확장한다.

## UX 어필 포인트

```text
직원 화면은 예쁜 화면보다 현장에서 클릭 수를 줄이고 현재 대기 상태를 빠르게 판단할 수 있는 구조를 우선했습니다.
```

## 면접 답변 후보

### 왜 MyBatis를 사용했나요?

```text
전자정부프레임워크 템플릿과 잘 맞고, 예약 가능 시간 조회나 대시보드 통계처럼 SQL을 명확히 제어해야 하는 기능이 많아서 MyBatis를 선택했습니다.
```

### 왜 프론트 흐름을 먼저 봤나요?

```text
예약·대기 시스템은 화면 흐름이 업무 효율에 직접 영향을 줍니다. 특히 직원 화면은 어떤 데이터가 한 번에 보여야 하는지가 중요해서, 화면별 필요한 API 계약을 먼저 정리한 뒤 백엔드 구현 범위를 잡았습니다.
```

### 가장 어려운 기능은 무엇인가요?

```text
예약 생성과 대기 상태 전이가 가장 중요합니다. 예약은 동시성 때문에 정원 초과를 막아야 하고, 대기는 WAITING, CALLED, IN_PROGRESS, HOLD, COMPLETED 상태 전이를 잘못 허용하면 현장 운영 데이터가 깨질 수 있기 때문입니다.
```

### 이 프로젝트가 단순 CRUD와 다른 점은 무엇인가요?

```text
예약 정보만 저장하는 것이 아니라 예약 이후 방문, 대기번호, 호출, 처리 완료, 대시보드 통계까지 연결했습니다. 즉 하나의 공공서비스 운영 흐름을 데이터로 모델링한 점이 다릅니다.
```
