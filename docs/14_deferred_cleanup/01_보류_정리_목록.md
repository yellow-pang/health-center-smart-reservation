# 보류 정리 및 후속 고도화 목록

## 1. 문서 목적

이 문서는 지금 바로 삭제하거나 바꾸기에는 애매한 정리 후보와, 백엔드 기능 개발이 어느 정도 끝난 뒤 진행할 후속 고도화 후보를 모아두는 곳이다.

작업 중 아래처럼 판단되는 항목은 즉시 삭제하지 않고 이 문서로 보낸다.

- eGovFrame 공통 골격과 연결되어 있어 영향 범위가 큰 항목
- 지금은 사용하지 않는 것처럼 보이지만 다른 설정, 테스트, 보안 흐름과 연결될 수 있는 항목
- MVP에서는 필요 없지만 포트폴리오 설명 또는 향후 확장 후보로 남길 수 있는 항목
- 삭제해도 될 가능성이 크지만 별도 브랜치에서 더 좁게 검증하는 편이 안전한 항목
- 보안, 트랜잭션, 권한, 성능, 운영성, UX/API 편의성 측면에서 나중에 고도화할 항목

이 문서는 “하지 않을 일 목록”이 아니라 “나중에 깔끔하게 정리하거나 더 좋게 만들 후보 목록”이다.

## 2. 기록 원칙

- 보류한 이유를 짧게 적는다.
- 지금 삭제하지 않은 이유를 적는다.
- 나중에 어떤 조건이 충족되면 정리할지 적는다.
- 관련 문서와 파일 경로를 남긴다.
- 기능 구현 브랜치와 정리 브랜치를 가능하면 분리한다.

## 3. 상태 값

| 상태 | 의미 |
|---|---|
| `보류` | 아직 판단하지 않고 남겨둔다. |
| `확인 필요` | 다음 정리 브랜치에서 참조와 영향 범위를 확인한다. |
| `제거 후보` | 제거 가능성이 높지만 별도 검증 후 삭제한다. |
| `유지 후보` | 계속 남길 가능성이 높지만 이유를 확정해야 한다. |
| `고도화 후보` | MVP 이후 품질, 성능, 보안, 운영성을 높이기 위해 진행할 수 있다. |
| `정리 완료` | 별도 브랜치에서 정리했고 결과 문서가 있다. |

## 5. 운영 관측성 및 부하 테스트 권장 도구

운영성 고도화는 한 번에 모두 붙이지 않고 아래 순서로 진행한다.

| 순서 | 도구 | 목적 | 프로젝트 적용 기준 |
|---:|---|---|---|
| 1 | Logback 구조화 로그 | 요청, 예외, 상태 변경 추적 | `traceId`, method, URI, status, latencyMs, memberId, role, errorCode를 남기고 개인정보는 마스킹한다. |
| 2 | Spring Boot Actuator + Micrometer | 애플리케이션 상태와 메트릭 노출 | health, JVM, HTTP server request, error rate, latency를 확인한다. |
| 3 | Prometheus | 메트릭 수집 | `/actuator/prometheus`를 scrape하고 API별 응답 시간과 오류율을 저장한다. |
| 4 | Grafana | 메트릭 시각화 | 예약/방문/대기/대시보드 API latency, request count, error rate, JVM 지표를 대시보드로 구성한다. |
| 5 | Loki | 로그 집계 | 부하 테스트 중 발생한 오류 로그를 Grafana에서 메트릭과 함께 조회한다. |
| 6 | k6 | 부하/스트레스 테스트 | 예약 신청, 현장 접수, 대기번호 발급, 대시보드 조회 시나리오를 작성한다. |
| 7 | OpenTelemetry | trace/log/metric 상관관계 고도화 | 기본 관측성 구성이 안정화된 뒤 Java Agent 또는 Spring Boot Starter 방식으로 검토한다. |

권장 구현 순서:

1. `feat/request-logging-audit-trace`: 요청/응답 로깅, 상태 변경 로그, 개인정보 마스킹 기준 추가
2. `feat/backend-observability-actuator`: Actuator, Micrometer, Prometheus endpoint와 보안 정책 추가
3. `chore/observability-compose-stack`: Prometheus, Grafana, Loki 구성을 Docker Compose에 추가
4. `test/k6-queue-load-scenarios`: k6 기반 예약/방문/대기 부하 테스트 시나리오 작성
5. `feat/opentelemetry-tracing`: OpenTelemetry trace 고도화 검토 및 적용

## 6. 나중에 처리할 때의 작업 순서

1. 이 문서에서 `확인 필요`, `제거 후보`, `고도화 후보` 항목을 하나 고른다.
2. 별도 브랜치를 만든다.
3. `rg`와 GitNexus가 가능하면 impact 분석으로 참조 범위를 확인한다.
4. 제거/유지/고도화 대상을 구현 기록에 먼저 적는다.
5. 한 기능 묶음만 작게 처리한다.
6. `mvn -q -DskipTests compile`과 `mvn -q test-compile`을 확인한다.
7. 서버 기동, API 호출, Swagger 확인은 사용자가 직접 수행할 명령과 기대 결과를 문서화한다.
8. 정리 결과를 이 문서에 반영한다.
